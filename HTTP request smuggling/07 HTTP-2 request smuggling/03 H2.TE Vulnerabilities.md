# H2.TE Vulnerabilities — Explained Simply

## The Setup: A Glitch in the Translation

You already know that HTTP/2 is a strict binary protocol, and it **does not support chunked encoding** (`Transfer-Encoding: chunked`). 

The security rules say: *"If an attacker tries to put `Transfer-Encoding: chunked` into an HTTP/2 request, the front-end server must strip it out or block the request."*

**The flaw:** Some front-end servers forget to strip it out. They just translate the request to HTTP/1.1 and pass it to the back-end. 

The back-end server (which speaks HTTP/1.1) sees the chunked encoding, obeys it, and gets confused. This is **H2.TE**.

---

## How the Attack Works

You send an HTTP/2 request that includes the forbidden `Transfer-Encoding: chunked` header, but you hide a request in the body:

### 1. What you send (HTTP/2)
```http
:method POST
:path /example
:authority vulnerable-website.com
content-type application/x-www-form-urlencoded
transfer-encoding chunked   <-- The Forbidden Header

0

GET /admin HTTP/1.1
Host: vulnerable-website.com
Foo: bar
```

### 2. The Front-End's Mistake
The front-end server uses HTTP/2 binary math to figure out the length. It doesn't validate the `transfer-encoding` header. It just translates the request into HTTP/1.1 and sends it to the back-end. 

### 3. The Back-End's Trap
The back-end server receives the HTTP/1.1 request. It sees `Transfer-Encoding: chunked` and switches to chunked mode. 

It reads the `0` chunk and says, *"End of request!"* 
It leaves the rest (`GET /admin...`) in its memory as the **next request**. 

### 4. The Exploit
Just like in standard TE.CL, the next user's request gets glued to the `GET /admin`. You have successfully smuggled a request past the front-end!

## 🕵️‍♂️ Bonus: Hidden HTTP/2 Support

The text mentions a tricky scenario called **Hidden HTTP/2 Support**. 

Sometimes, a server actually *does* support HTTP/2, but its configuration is broken, so it doesn't advertise it. Your browser (and Burp) will default to HTTP/1.1, and you'll think the server is safe. 

**How to check for it in Burp:**
1. Go to Burp **Settings** > **Tools** > **Repeater**.
2. Check **"Allow HTTP/2 ALPN override"**.
3. In Repeater, go to **Inspector** > **Request attributes** and force the protocol to **HTTP/2**.
4. Send your request. If the server accepts it, it means HTTP/2 was secretly supported all along, and you can test it for H2.CL or H2.TE vulnerabilities!

### The One-Sentence Summary
> **H2.TE = You inject a forbidden `Transfer-Encoding: chunked` header into an HTTP/2 request. The front-end doesn't strip it, passes it to the back-end, and the back-end stops early, leaving your smuggled request in memory.** 🎯
