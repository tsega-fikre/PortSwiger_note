# TE.CL Vulnerabilities — Full Walkthrough

## The Setup
- **Front-end** uses `Transfer-Encoding: chunked` to find where the request ends.
- **Back-end** uses `Content-Length` to find where the request ends.

They're looking at the same bytes, but using different rulers. 

---

## The Attack Request

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 3
Transfer-Encoding: chunked

8
SMUGGLED
0

```

*(Note: In Burp, you **must** turn off "Update Content-Length" in the Repeater menu, otherwise Burp will automatically change the `3` and break the attack. Also, make sure there is a `\r\n\r\n` after the final `0`.)*

---

## Step 1 — What the Front-End Sees (Chunked)

The front-end trusts `Transfer-Encoding: chunked` and completely ignores `Content-Length`. It reads the body as chunks:

1. `8\r\n` → "The first chunk is 8 bytes long."
2. `SMUGGLED\r\n` → (Exactly 8 bytes! ✅)
3. `0\r\n\r\n` → "The next chunk is 0 bytes. **End of request.**"

The front-end sees one complete, clean request. It forwards the entire thing to the back-end.

---

## Step 2 — What the Back-End Sees (Content-Length)

The back-end trusts `Content-Length: 3` and completely ignores `Transfer-Encoding`. It counts exactly **3 bytes**:

```text
8\r\n
```
*(That's `8` (1 byte) + `\r\n` (2 bytes) = 3 bytes).*

The back-end says: "The request body is 3 bytes. **Request ends here.**"

---

## Step 3 — The Leftover Bytes

Because the back-end stopped after 3 bytes, everything else is left sitting in its input buffer:

```text
SMUGGLED\r\n
0\r\n\r\n
```

The back-end treats these leftover bytes as **the start of the next request**. 

When the next legitimate request arrives, it gets appended to `SMUGGLED`. The attacker has successfully injected `SMUGGLED` into the queue!

---

## The Visual

```text
Bytes on the wire:
┌─────────────────────────────────────────┐
│ POST / HTTP/1.1                         │
│ Content-Length: 3                       │
│ Transfer-Encoding: chunked              │
│                                         │
│ 8                                       │ ← back-end: "3 bytes done! Request ends."
│ SMUGGLED                                │ ← front-end: "8 bytes of chunk data, all good"
│ 0                                       │
│                                         │
└─────────────────────────────────────────┘
```

- **Front-end boundary:** After the `0\r\n\r\n` (the end of the chunks).
- **Back-end boundary:** After `8\r\n` (3 bytes).
- **The gap:** `SMUGGLED...` = the smuggled payload.

---

## Why This Works

1. The **front-end supports chunked encoding** and follows the rules perfectly.
2. The **back-end doesn't support chunked** (or ignores it) and falls back to `Content-Length`. 

Because the back-end stops reading way earlier than the front-end expects, the leftover data poisons the connection.

---

## One-Sentence Summary

> **TE.CL = the front-end reads the whole chunked body and forwards it; the back-end reads only the first 3 bytes (`8\r\n`), stops early, and treats the rest (`SMUGGLED`) as the start of the next request.** 

The trick relies on the `8\r\n` looking like a valid 3-byte body to the back-end, while looking like a chunk header to the front-end. 🔓
