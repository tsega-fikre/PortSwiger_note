# CL.TE Vulnerabilities — Full Walkthrough

## The Setup

- **Front-end** uses `Content-Length` to find where the request ends.
- **Back-end** uses `Transfer-Encoding: chunked` to find where the request ends.

They're reading the **same bytes** but using **different rulers**. That's the whole vulnerability.

---

## The Attack Request

```
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 13
Transfer-Encoding: chunked

0

SMUGGLED
```

---

## Step 1 — What the Front-End Sees

The front-end trusts `Content-Length: 13`. It counts **13 bytes** of body:

```
0\r\n
\r\n
SMUGGLED
```

Let's count: `0` (1) + `\r\n` (2 more = 3) + `\r\n` (2 more = 5) + `SMUGGLED` (8 more = **13**). ✅

So the front-end says: **"Request body is 13 bytes. Ends right after SMUGGLED. Forwarding to back-end."**

The front-end sees **one complete, harmless request**. Nothing suspicious. It forwards the whole thing — headers + those 13 bytes — to the back-end.

---

## Step 2 — What the Back-End Sees

The back-end trusts `Transfer-Encoding: chunked`. It ignores `Content-Length` entirely and reads the body **as chunks**:

```
0        ← chunk size = 0 (hex) = zero-length chunk = END OF REQUEST
```

The **first chunk is size 0**. In chunked encoding, a zero-size chunk means **"the request is done."** So the back-end stops reading right there.

Everything after that — the blank line and `SMUGGLED` — is **left over, unprocessed**.

---

## Step 3 — The Leftover Bytes

The back-end has finished the request, but there are still bytes sitting in its input buffer:

```
SMUGGLED
```

What does a server do with leftover bytes on a connection? It treats them as **the start of the next request**.

So the back-end now thinks the next request begins with `SMUGGLED`. It will wait for the rest of that request to arrive — and that "rest" will be **the next legitimate user's request**, which gets appended right after.

Result: the next user's request gets **prefixed with `SMUGGLED`** — corrupted, hijacked, or used to trigger attacker-controlled behavior. And the front-end never saw any of it, because it thought those bytes were just body content.

---

## The Visual

```
Bytes on the wire:
┌──────────────────────────────────────────────┐
│ POST / HTTP/1.1                               │
│ Content-Length: 13                            │
│ Transfer-Encoding: chunked                    │
│                                               │
│ 0                                             │ ← back-end: "request ends here!"
│                                               │
│ SMUGGLED                                      │ ← front-end: "still body (13 bytes)"
└──────────────────────────────────────────────┘
        │                              │
        │                              └─ leftover → start of NEXT request
        └─ front-end: "one clean request, 13-byte body"
```

- **Front-end's boundary:** after `SMUGGLED` (byte 13)
- **Back-end's boundary:** after the `0` chunk (much earlier)

The gap between the two boundaries = the smuggled payload.

---

## Why This Works (The Two Conditions)

1. **The front-end doesn't support / doesn't honor `Transfer-Encoding`** in requests — or honors it differently — so it falls back to `Content-Length`.
2. **The back-end honors `Transfer-Encoding`** and follows the spec rule: "if both headers present, ignore `Content-Length`."

Each server is behaving **correctly by its own rules**. The bug is that their rules **disagree**.

---

## The Key Insight

The `0` chunk is doing double duty:

- To the **front-end**, `0` is just a byte of body data (part of the 13).
- To the **back-end**, `0` is the **terminator** — "stop here."

That's the trick. One byte, two meanings, two different boundaries.

---

## What an Attacker Does With It

Once `SMUGGLED` is sitting in the back-end's queue, the attacker shapes it into a **real request** — e.g., `GET /admin HTTP/1.1` — so that when the next victim's request arrives, the back-end processes the smuggled request **first**, under the victim's connection. That enables:

- **Bypassing front-end auth** (the hidden request never passed the front-end)
- **Capturing the next user's request** (session/cookie theft)
- **Cache poisoning**
- **Response queue desync**

---

## One-Sentence Summary

> **CL.TE = the front-end counts 13 bytes and forwards the whole thing; the back-end hits the `0` chunk, stops early, and treats the leftover `SMUGGLED` as the start of the next request — a request the front-end never inspected.**

The `0` chunk is the pivot point: **body byte to one server, terminator to the other.** 🔓
