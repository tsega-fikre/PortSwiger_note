# TE.TE Obfuscation — Explained Simply

## The Setup
Both servers support chunked encoding (`Transfer-Encoding`). In theory, they should agree. But they don't, because of one simple reason:

> **One server is pickier about spelling than the other.**

## The Trick
HTTP rules say the header must be exactly `Transfer-Encoding: chunked`. But real-world servers are sloppy. If you write it slightly wrong (a typo, a weird space, a hidden tab):

- **Server A (the lenient one):** Reads it anyway → uses chunked encoding.
- **Server B (the strict one):** Says "I don't recognize that header" → ignores it and falls back to `Content-Length`.

Now they disagree on where the request ends. **That's the vulnerability.**

## Examples of "Wrong" Headers
You try variations until you find one that one server accepts and the other rejects:
- `Transfer-Encoding: xchunked` (typo)
- `Transfer-Encoding : chunked` (extra space before colon)
- `Transfer-Encoding:[tab]chunked` (tab instead of space)
- Two `Transfer-Encoding` headers (one valid, one fake)

## What Happens Next
Once you find the magic variation that fools one server:

- If the **front-end ignores it** and the back-end uses it → the attack plays out exactly like **CL.TE**.
- If the **front-end uses it** and the back-end ignores it → the attack plays out exactly like **TE.CL**.

## The One-Sentence Summary
> **TE.TE = both servers speak chunked, but you spell the header weirdly so only one of them understands it. Then you just run the CL.TE or TE.CL attack from there.**
