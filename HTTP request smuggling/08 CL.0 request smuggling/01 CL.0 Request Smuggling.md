# CL.0 Request Smuggling — Explained Simply

## The Setup: The "Rule Follower" and the "Rule Ignorer"

Normally, when a server receives a request, it looks at the `Content-Length` header to know how long the body is. If `Content-Length: 10`, it reads exactly 10 bytes.

**CL.0** happens when the **back-end server completely ignores the `Content-Length` header** (or treats it as `0`). It assumes the request ends immediately after the headers.

The **front-end server**, however, still uses `Content-Length` to calculate where the request ends. 

## The Trick

Because the back-end ignores the length, you can just put a hidden request in the body. The back-end will think it's a brand-new request, while the front-end thinks it's just body data.

Here is an example:

```http
POST / HTTP/1.1
Host: vulnerable-website.com
Content-Length: 34

GET /admin HTTP/1.1
Host: vulnerable-website.com
```

### What the Front-End Sees:
It reads `Content-Length: 34` and counts exactly 34 bytes. It sees this as **one single POST request** and forwards it to the back-end.

### What the Back-End Sees:
It completely ignores `Content-Length`. It sees the blank line after the headers and says, *"End of request!"* 

It leaves the `GET /admin HTTP/1.1...` sitting in its memory as the **next request**. 

---

## Why is this dangerous?

You can use CL.0 to perform many of the same attacks we just did, without needing chunked encoding or conflicting headers. You just drop the `Content-Length` trick right into a normal-looking request, and the back-end blindly processes the hidden payload.

### The One-Sentence Summary:
> **CL.0 = The front-end uses `Content-Length` to read the whole body, but the back-end ignores `Content-Length` and stops at the end of the headers, leaving your hidden body as the next request.** 🎯
